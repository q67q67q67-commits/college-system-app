# Анализ проекта Narxoz College (NC)

Документ описывает текущее состояние проекта, возможные недочёты (с упором на бэкенд), направление развития и шаги для доведения проекта до конца.

---

## 1. Текущее состояние проекта

### 1.1. Что реализовано

**Инфраструктура и БД:**
- Структура репозитория: `cmd/api`, `internal/`, `api/`, `migrations/`, `docs/`, `design-prototypes/`.
- PostgreSQL в Docker (`docker-compose.yml`), миграции при первом запуске.
- Схема БД: `users` (роли, лимит 2 ГБ), `groups`, `user_groups`, `schedules`, `schedule_attachments`, `grades`, `forum_posts`, `library_books`, `library_copies`, `library_reservations`, `events`, `user_files` (с триггером квоты).

**Авторизация:**
- `POST /auth/login` (email + password), ответ с JWT и данными пользователя.
- Middleware: проверка JWT (`RequireAuth`), ограничение по ролям (`RequireRole`).
- Тестовые пользователи в сиде (director, admin, teachers, students), пароль `password123`.

**API по доменам:**
- **Расписание:** GET расписания (по группе для студента, по преподавателю для teacher), GET дополнений к паре (ДЗ/уведомления).
- **Оценки:** GET журнал/GPA/транскрипт для студента; POST/PUT/DELETE оценок для преподавателя.
- **Группы:** GET список групп, GET студенты группы.
- **Библиотека:** GET поиск книг, GET экземпляры с владельцами, POST бронирование.
- **Форум:** GET список постов (темы/ответы), POST создание поста (с флагом `is_anonymous`).
- **События:** GET список/одно событие (фильтры по дате и поиску), POST/PUT/DELETE для admin/director.
- **Файлы:** GET список + квота, POST загрузка (с проверкой 2 ГБ), DELETE файла.
- **Чат:** WebSocket `GET /api/chat/ws` — один общий чат (broadcast всем).

**Документация и онбординг:**
- `api/ENDPOINTS.md` — список эндпоинтов с примерами JSON.
- `context.md` — контекст проекта, роли, онбординг для Б/Ф.
- `docs/FRONTEND_TUTORIAL.md` — пошаговый туториал для фронтенда (задачи 9–15).
- `docs/GITHUB_TUTORIAL.md` — работа с GitHub и ветками.

**Фронтенд (Фаза 2):** не реализован; задачи 9–15 выполняются отдельным участником по туториалу.

## 2. Возможные недочёты (с учётом бэкенда)

### 2.1. Отсутствующий функционал по ТЗ (Заметки.md)

| Требование | Текущее состояние | Рекомендация |
|------------|-------------------|--------------|
| **Статус студента: кредиты, летний семестр, задолженности** | Нет таблиц и API. | Ввести сущность «академический статус» (кредиты, долги, летний семестр): таблица или поля в `users`/связка со студентом + GET API для студента. |
| **Регламент обучения: академический календарь + силлабус** | Нет таблиц и API. | Добавить сущности (календарь, привязка документов/силлабуса) и API чтения; либо статичные файлы + эндпоинт списка. |
| **Профиль директора «Twitter»: шапка, фото, описание, посты, закреплённые** | Нет таблиц и API. | Таблица `director_profile` (banner_url, bio и т.д.) и `director_posts` (контент, is_pinned). API: GET публичного профиля директора, CRUD постов (только director). |
| **Оповещения для студентов и преподавателей** | Нет. | Таблица `notifications` (user_id, title, body, read_at, created_at), API: GET список, PATCH прочитать. Опционально: push (FCM и т.д.). |
| **Личные и групповые чаты** | Реализован только общий WebSocket. | Таблицы `conversations`, `conversation_members`, `chat_messages`. API: список диалогов/комнат, история сообщений (REST), WebSocket с комнатами по conversation_id. |
| **Комментарии/отзывы к событиям** | Нет. | Таблица `event_comments` (event_id, user_id, body, attachments). API: GET/POST комментариев к событию. |
| **Смена пароля и номера телефона** | Нет API. | GET/PUT `/api/profile` (текущий пользователь): чтение профиля, обновление phone; отдельно PUT `/api/profile/password` (старый пароль + новый). |
| **Связаться / техподдержка** | Нет. | Таблица заявок (тикетов) и API создания/просмотра для пользователя; просмотр/закрытие для admin. |
| **Админ-панель: «все нужные функции»** | Не формализовано. | Уточнить: управление пользователями (список, смена роли, блокировка), просмотр логов, настройки. Добавить API под выбранный набор. |
| **Доступ к аккаунту год после ухода** | Поле `users.left_at` есть, проверки нет. | В middleware или при логине проверять: если `left_at` задан и прошло > 1 года — 403 или отказ в логине. |
| **Папки и шаринг в «Мои файлы»** | Только плоский список, path как строка. | Модель папок (parent_id в user_files или отдельная таблица), API создания папок; отдельно — шаринг (ссылка/токен доступа к папке). |

### 2.2. Технические и эксплуатационные недочёты

| Недочёт | Описание | Рекомендация |
|---------|----------|--------------|
| **CORS** | Заголовки CORS не выставляются. | Добавить middleware CORS (AllowOrigin, методы, заголовки) для запросов с веб-фронта с другого origin. |
| **Скачивание файлов** | Есть загрузка и удаление, нет скачивания по id. | GET `/api/files/{id}` или `/api/files/{id}/download` — отдача файла с проверкой владельца (и прав при шаринге). |
| **Refresh token** | Только access JWT, без refresh. | По необходимости: выдача refresh-токена при логине, эндпоинт обмена refresh на access; хранение/инвалидация refresh на стороне БД. |
| **Валидация входных данных** | Минимальная (непустые поля и т.д.). | Единообразная валидация: формат email, диапазон оценок, даты, размер файла; возврат 400 с перечнем ошибок. |
| **Rate limiting** | Нет ограничения частоты запросов. | Middleware rate limit на `/auth/login` и при необходимости на другие эндпоинты (по IP или по user_id). |
| **Логирование** | Только отдельные log.Printf. | Структурированное логирование запросов (method, path, status, duration), ошибок и при необходимости трейсов. |
| **Конфигурация и секреты** | JWT secret и DB URL из env, дефолты для разработки. | В проде: обязательные env, без дефолтов для секретов; вынести конфиг в отдельный слой (config validation при старте). |
| **Права на записи** | Частично (роли по эндпоинтам). | Где нужно: проверка «ресурс принадлежит пользователю или его группе» (например, оценка — только за своих студентов по своему расписанию). |

### 2.3. Архитектура и код

- **Глобальный пул БД** (`internal/db`): для текущего масштаба допустимо; при росте — внедрение зависимостей (DI) и возможность тестов с подменой БД.
- **Контекст пользователя в handlers:** передача user_id/роли через заголовки после middleware — рабочий вариант; при усложнении логики удобнее `context.Context` с полями пользователя.
- **Нет юнит/интеграционных тестов:** добавление тестов на критические сценарии (логин, квоты, роли) повысит надёжность при доработках.

## 3. Направление развития проекта

### 3.1. Целевое состояние

- **Бэкенд:** стабильный API, покрывающий все сценарии из Заметок (включая статус студента, профиль директора, чаты, уведомления, профиль и смену пароля), с CORS, валидацией, ограничением частоты запросов и логированием.
- **Фронтенд (Flutter):** реализованные задачи 9–15 по `docs/FRONTEND_TUTORIAL.md`, адаптивная вёрстка (Web/Mobile), все роли и сценарии.
- **Эксплуатация:** конфигурация через env, возможность деплоя (Docker для API + БД), при необходимости — CI/CD и мониторинг.

### 3.2. Приоритеты

1. **Критично для запуска фронта:** CORS, при необходимости — GET профиля и скачивание файлов.
2. **Важно по ТЗ:** профиль и смена пароля/телефона, статус студента (кредиты/долги), профиль директора и посты, комментарии к событиям.
3. **Социум и коммуникация:** личные/групповые чаты, уведомления, техподдержка/тикеты.
4. **Качество и безопасность:** валидация, rate limiting, проверка `left_at`, логирование, тесты.
5. **Расширения:** регламент/календарь/силлабус, папки и шаринг файлов, админ-панель (управление пользователями и т.д.).

## 4. Шаги, чтобы довести проект до конца

### Фаза A. Минимум для работы фронтенда (бэкенд)

1. **CORS:** добавить middleware CORS в `cmd/api/main.go` (настройка origin, методов, заголовков).
2. **GET /api/profile:** возврат данных текущего пользователя (id, email, full_name, role, phone, language, avatar_url, storage_used/storage_limit).
3. **PUT /api/profile:** обновление full_name, phone, language (и при необходимости avatar_url).
4. **PUT /api/profile/password:** смена пароля (тело: current_password, new_password); проверка текущего пароля, хеширование нового.
5. **GET /api/files/{id}/download:** отдача файла по id с проверкой, что файл принадлежит текущему пользователю (Content-Disposition и т.д.).
6. **Проверка left_at:** в middleware или при логине: если `left_at` не null и прошло более 1 года — возвращать 403 или не выдавать токен, с сообщением о прекращении доступа.

Обновить `api/ENDPOINTS.md` и при необходимости `context.md`.

### Фаза B. Закрытие пробелов по ТЗ (бэкенд)

7. **Статус студента:** таблица или поля (кредиты, летний семестр, задолженности); GET `/api/student/status` для студента.
8. **Профиль директора:** таблицы `director_profile` и `director_posts` (с is_pinned); GET `/api/director/profile` (публичный), GET/POST/PUT/DELETE постов (для director).
9. **Комментарии к событиям:** таблица `event_comments`, GET/POST для комментариев к событию (при необходимости — вложения).
10. **Уведомления:** таблица `notifications`, GET список (с пагинацией и фильтром «не прочитано»), PATCH прочитать.
11. **Регламент/календарь/силлабус:** минимальный вариант — таблица «события календаря» + ссылки на документы или хранение файлов; GET API для отображения на фронте.

Документировать новые эндпоинты и обновить фронтенд-туториал по мере появления API.

### Фаза C. Чаты и коммуникация (бэкенд)

12. **Личные и групповые чаты:** схема БД (conversations, members, messages), REST: список диалогов, история сообщений, создание диалога/комнаты; WebSocket: подписка на комнаты по conversation_id, сохранение сообщений в БД и рассылка участникам.
13. **Техподдержка:** таблица обращений (тикеты), POST создание от пользователя, GET список своих, GET/PATCH для админа (статус, ответ).

### Фаза D. Фронтенд и интеграция

14. **Фронтенд (Фаза 2):** по `docs/FRONTEND_TUTORIAL.md` реализовать задачи 9–15 (навигация, Auth, главная, учебный процесс, социум, профили и файлы, финализация). Подключать новые эндпоинты по мере их появления (профиль, директор, комментарии, уведомления, чаты).
15. **Согласование контрактов:** при расхождении ответов API с ожиданиями фронта — править бэкенд или фронт и обновлять `api/ENDPOINTS.md`.

### Фаза E. Качество и подготовка к релизу

16. **Валидация и ошибки:** единый формат ошибок (код, сообщение, опционально поля), валидация тел запросов.
17. **Rate limiting:** на логин и при необходимости на чувствительные эндпоинты.
18. **Логирование:** структурированные логи запросов и ошибок.
19. **Тесты:** юнит-тесты на сервисы/хендлеры, интеграционные на ключевые сценарии (логин, квота, роли).
20. **Деплой:** Dockerfile для API, docker-compose для API + БД, пример env для продакшена; при необходимости — CI (сборка, тесты), документация по развёртыванию.

### Фаза F. Доработки по приоритету

21. **Админ-панель (бэкенд):** API управления пользователями (список, фильтры, смена роли, блокировка), если входит в объём «все нужные функции».
22. **Папки и шаринг файлов:** модель папок, API папок и шаринга (публичные ссылки или доступ по токену).
23. **Refresh token и безопасность:** при необходимости — refresh-токены, инвалидация при смене пароля, ужесточение политики JWT.
