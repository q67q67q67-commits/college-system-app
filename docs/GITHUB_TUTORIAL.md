# Туториал: GitHub с нуля для проекта NC

Пошаговая инструкция для абсолютных новичков: как выложить проект на GitHub и как второму участнику с ним работать (ветки, слияние в main).

---

## Часть 1. Подготовка: установка Git и настройка

### Шаг 1.1. Установить Git

1. Скачайте Git: https://git-scm.com/downloads  
2. Установите с настройками по умолчанию (Next → Next).  
3. Проверьте в терминале (PowerShell или cmd):

```bash
git --version
```

Должна появиться строка вида `git version 2.x.x`.

### Шаг 1.2. Настроить имя и email (один раз на компьютере)

В терминале выполните (подставьте свои данные):

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваш-email@example.com"
```

Email лучше использовать тот же, что привязан к аккаунту GitHub — так ваши коммиты будут отображаться в профиле.

---

## Часть 2. Создать репозиторий на GitHub с нуля

### Шаг 2.1. Аккаунт GitHub

1. Зайдите на https://github.com  
2. Если аккаунта нет — нажмите **Sign up** и зарегистрируйтесь.  
3. Войдите в аккаунт.

### Шаг 2.2. Новый репозиторий

1. В правом верхнем углу нажмите **+** → **New repository**.  
2. Заполните:
   - **Repository name:** например `NC` или `narxoz-college` (латиница, без пробелов).
   - **Description:** по желанию, например «Narxoz College — мобильное и веб-приложение».
   - **Public** или **Private** — на ваш выбор.
   - **НЕ** ставьте галочку «Add a README file» — проект уже есть у вас локально.  
3. Нажмите **Create repository**.

После создания GitHub покажет страницу с подсказками. Пока её можно не использовать — дальше всё сделаем из папки проекта.

## Часть 3. Положить проект в Git и отправить на GitHub

Все команды выполняются в терминале **в корне проекта** (папка, где лежат `go.mod`, `context.md`, папки `cmd`, `internal` и т.д.).

### Шаг 3.1. Открыть терминал в папке проекта

- В VS Code / Cursor: меню **Terminal** → **New Terminal** (или `` Ctrl+` ``).  
- Либо откройте PowerShell, перейдите в папку:

```bash
cd d:\Projects\NC
```

### Шаг 3.2. Инициализировать репозиторий

```bash
git init
```

Появится строка: `Initialized empty Git repository in .../NC/.git/`  
В папке появится скрытая папка `.git` — это и есть репозиторий.

### Шаг 3.3. Файл .gitignore (что не пушить)

Чтобы не загружать на GitHub лишнее (бинарники, кэш, ключи), создайте в корне проекта файл **`.gitignore`** со следующим содержимым:

```
# Go
*.exe
*.exe~
*.dll
*.so
*.dylib
*.test
*.out
vendor/
.env
.env.local
*.log

# IDE / OS
.idea/
.vscode/
*.swp
.DS_Store
Thumbs.db
```

Сохраните файл в корне: `d:\Projects\NC\.gitignore`.

### Шаг 3.4. Первый коммит

По очереди выполните:

```bash
git add .
```

Эта команда добавляет в «индекс» все файлы из папки (кроме тех, что в `.gitignore`).

Проверить, что будет в коммите:

```bash
git status
```

Должны быть перечислены файлы (main.go, context.md, migrations и т.д.). Если видите лишнее — добавьте его в `.gitignore` и снова `git add .`.

Создать первый коммит:

```bash
git commit -m "Initial: structure, docker-compose, DB schema, context"
```

Сообщение после `-m` — краткое описание изменений. Его будет видно в истории.

### Шаг 3.5. Переименовать ветку в main (если нужно)

В новых версиях Git ветка по умолчанию может называться `main`. Проверить:

```bash
git branch
```

Если видите `master`, переименуйте:

```bash
git branch -M main
```

### Шаг 3.6. Подключить удалённый репозиторий GitHub

Замените `ВАШ_ЛОГИН` и `НАЗВАНИЕ_РЕПО` на свои (как на GitHub):

```bash
git remote add origin https://github.com/ВАШ_ЛОГИН/НАЗВАНИЕ_РЕПО.git
```

Пример: если репозиторий создан как `myuser/NC`:

```bash
git remote add origin https://github.com/myuser/NC.git
```

Проверить:

```bash
git remote -v
```

Должны быть строки с `origin` и вашим URL.

### Шаг 3.7. Отправить код на GitHub (первый push)

```bash
git push -u origin main
```

- GitHub может попросить войти (логин и пароль или токен).  
- Если просит пароль — используйте **Personal Access Token**, а не обычный пароль: GitHub → Settings → Developer settings → Personal access tokens → создать токен с правом `repo`.  
- После успешного push на странице репозитория на GitHub появятся все файлы.

## Часть 4. Второй участник: клонирование и работа в своей ветке

Ниже — как **другому человеку** (или вам с другого компьютера) подключиться к проекту и работать в отдельной ветке, не мешая main.

### Шаг 4.1. Клонировать репозиторий

В папке, где хотите держать проект (например `d:\Projects`), выполните:

```bash
git clone https://github.com/ВАШ_ЛОГИН/НАЗВАНИЕ_РЕПО.git
cd НАЗВАНИЕ_РЕПО
```

Вместо URL можно скопировать ссылку с кнопки **Code** на странице репозитория на GitHub (HTTPS).

В папке появится полная копия проекта и скрытая `.git`.

### Шаг 4.2. Создать свою ветку (для каждого участника отдельно)

Рекомендуется: у каждого участника своя ветка (или одна общая ветка на Backend, одна на Frontend).

Примеры имён веток:

- `backend` — тот, кто делает Go API  
- `frontend` — тот, кто делает Flutter  
- или по имени: `ivanov`, `petrova`

Создать ветку и сразу переключиться на неё:

```bash
git checkout -b backend
```

Проверить текущую ветку:

```bash
git branch
```

Звёздочка будет рядом с `backend`.

### Шаг 4.3. Работа в своей ветке: правки и push

1. Делаете изменения в файлах (код, миграции, документы).  
2. Посмотреть, что изменилось:

```bash
git status
git diff
```

3. Добавить изменения и закоммитить:

```bash
git add .
git commit -m "Описание изменений: например, добавлен сидинг БД"
```

4. Отправить **свою ветку** на GitHub (первый раз для этой ветки):

```bash
git push -u origin backend
```

Дальше можно просто:

```bash
git push
```

Все последующие правки в этой ветке: `git add .` → `git commit -m "..."` → `git push`.

### Шаг 4.4. Подтянуть изменения из main (если кто-то уже что-то влил)

Перед тем как продолжать работу или делать Pull Request, лучше обновить свою ветку из main:

```bash
git fetch origin
git merge origin/main
```

Или одной командой (если уже настроено отслеживание):

```bash
git pull origin main
```

Если появятся конфликты — Git напишет, в каких файлах. Их нужно открыть, убрать маркеры конфликта и оставить нужный код, затем:

```bash
git add .
git commit -m "Resolve merge with main"
git push
```

## Часть 5. Слияние ветки в main (через Pull Request)

Когда участник закончил задачу в своей ветке и хочет «закинуть» изменения в main:

### Шаг 5.1. Убедиться, что ветка запушена

```bash
git push origin backend
```

(или какое у вас имя ветки)

### Шаг 5.2. Создать Pull Request на GitHub

1. Откройте репозиторий на GitHub.  
2. Появится жёлтая полоска: **«backend had recent pushes»** с кнопкой **Compare & pull request**. Или нажмите вкладку **Pull requests** → **New pull request**.  
3. Выберите:
   - **base:** `main`  
   - **compare:** `backend` (ваша ветка)  
4. Заполните заголовок и описание (что сделано, что проверено).  
5. Нажмите **Create pull request**.

### Шаг 5.3. Проверка и слияние (merge)

- Второй участник или вы открываете PR, смотрите изменения (вкладка **Files changed**).  
- Если всё ок — нажимаете **Merge pull request**, затем **Confirm merge**.  
- После этого ветка `main` на GitHub будет содержать все изменения из `backend`.  
- При желании можно удалить ветку `backend` (кнопка **Delete branch** после слияния) — локально каждый может удалить свою ветку: `git branch -d backend`.

### Шаг 5.4. Обновить локальный main у всех

У каждого на компьютере в папке проекта:

```bash
git checkout main
git pull origin main
```

Дальше можно снова создать ветку от актуального main и работать:

```bash
git checkout -b backend
# или продолжить в старой ветке после merge:
git checkout backend
git merge main
```

## Краткая шпаргалка команд

| Действие | Команда |
|----------|--------|
| Статус и изменения | `git status` / `git diff` |
| Добавить всё в коммит | `git add .` |
| Закоммитить | `git commit -m "Текст"` |
| Отправить ветку | `git push -u origin ИМЯ_ВЕТКИ` или `git push` |
| Подтянуть main | `git checkout main` → `git pull origin main` |
| Создать ветку | `git checkout -b ИМЯ_ВЕТКИ` |
| Переключить ветку | `git checkout main` / `git checkout backend` |
| Слить main в текущую ветку | `git merge origin/main` |

## Рекомендуемый порядок работы в проекте NC

1. **main** — только стабильный, уже проверенный код (после PR и merge).  
2. **Участник Б (Backend):** ветка `backend` (или `feature/backend`) — коммиты сюда, затем PR в main.  
3. **Участник Ф (Frontend):** ветка `frontend` — коммиты сюда, затем PR в main.  
4. Перед началом работы каждый делает `git pull origin main`, создаёт/обновляет свою ветку и работает в ней.  
5. Когда задача готова — Push → Pull Request → просмотр → Merge в main.  
6. После merge все делают `git checkout main` и `git pull origin main`.

Так конфликты будут решаться в PR, а main остаётся рабочим состоянием проекта.
